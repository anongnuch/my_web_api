# BRD → SA → Jira

ทำงาน 3 ช่วงต่อกัน: สกัดความต้องการจาก BRD → สร้างเอกสาร SA → สร้างการ์ด Jira ให้ dev
ห้ามข้ามไปสร้างการ์ด Jira ก่อนมีเอกสาร SA เพราะการ์ดทุกใบต้องอ้างอิง ID ของ SA ได้

## ช่วงที่ 1 — สกัดความต้องการจาก BRD

อ่าน BRD แล้วดึงออกมาเป็นตาราง ก่อนเขียนอะไรต่อ

| สิ่งที่ต้องดึง | รหัส | ถ้า BRD ไม่มี |
|---|---|---|
| Actor และสิทธิ์ | - | ตั้งสมมติฐานจากบริบท แล้วระบุไว้ท้ายเอกสาร |
| ความต้องการเชิงหน้าที่ | FR-001, FR-002, ... | ต้องถามผู้ใช้ ห้ามเดา เพราะ FR เป็นตัวตั้งของการ์ด Jira |
| กฎทางธุรกิจ | BL-001, ... | ตั้งสมมติฐานแล้วระบุไว้ |
| ความต้องการที่ไม่ใช่เชิงหน้าที่ | NFR-001, ... | ข้ามได้ แต่ต้องบันทึกว่าไม่มี |

**กฎ:** 1 FR = 1 Use Case = 1 User Story = 1 Jira Story เสมอ ถ้า FR ใหญ่เกิน 8 story points ให้ซอย FR เป็น FR-002a / FR-002b แล้วแจ้งผู้ใช้ว่าซอยเพราะอะไร

## ช่วงที่ 2 — เอกสาร SA

สร้างไฟล์เดียวที่ `docs/sa/SA-<nnn>-<slug>.md` มี 7 ส่วนตามลำดับนี้

| # | ส่วน | ใช้เป็นต้นฉบับของ |
|---|---|---|
| 1 | Requirement Mapping (FR ↔ UC ↔ US ↔ TC) | ตรวจความครบถ้วน |
| 2 | Use Case Specification | รายละเอียดใน Story |
| 3 | User Story + Acceptance Criteria | Jira Story |
| 4 | Flow Diagram (เฉพาะ FR ที่มี decision ซ้อน) | ใช้สื่อสารในทีม |
| 5 | API Contract + Data Model | Jira Subtask ฝั่ง BE และ DB |
| 6 | Test Case | Jira Subtask ฝั่ง QA |
| 7 | Traceability Matrix | ตรวจว่าทุก FR มีการ์ดรองรับ |

รูปแบบของส่วนที่ 2, 3, 4, 6 ใช้เทมเพลตเดียวกับ skill `sa-document-generator` (UC-xxx / US-xxx / ASCII flow / ตาราง TC) เพื่อให้เอกสารทั้งองค์กรหน้าตาเหมือนกัน
ส่วนที่ 5 และ 7 เป็นของ skill นี้เพิ่มเข้ามา เพราะเป็นสิ่งที่ dev ต้องใช้ตอนลงมือทำจริง

**กฎเนื้อหา**
- เนื้อหาภาษาไทย label ภาษาอังกฤษ
- ทุก Acceptance Criteria ต้องวัดผลได้ อ้าง HTTP status หรือค่าที่ตรวจได้ ห้ามเขียนว่า "ทำงานถูกต้อง"
- ทุก AC และทุก Exception Flow ต้องผูกกลับไปที่ BL หรือ NFR ที่เป็นที่มา
- Test Case ต้องมีทั้ง Positive และ Negative และต้องครอบคลุมทุก Exception Flow ของ UC นั้น

## ช่วงที่ 3 — Jira Pattern

### โครงสร้างการ์ด

```
Epic       1 ใบต่อ 1 BRD
  └─ Story   1 ใบต่อ 1 FR          (ผู้รับผิดชอบภาพรวมของ FR)
       └─ Subtask  แยกตามชั้นงาน   (หน่วยที่ dev หยิบทำจริง)
```

### รูปแบบ Summary

| ระดับ | รูปแบบ | ตัวอย่าง |
|---|---|---|
| Epic | `[<BRD-ID>] <ชื่อระบบ>` | `[BRD-001] ระบบบันทึกความเคลื่อนไหวสินค้าคงคลัง` |
| Story | `[<FR-ID>] <ชื่อความสามารถ>` | `[FR-002] เบิกสินค้าออกจากคลัง` |
| Subtask | `[<LAYER>][<FR-ID>] <งานที่ทำ>` | `[BE][FR-002] POST /api/stock/issue` |

ค่า `<LAYER>` ใช้ได้เฉพาะ: `DB` (schema/migration), `BE` (API/business logic), `FE` (หน้าจอ), `QA` (test), `DOC` (เอกสาร/Swagger)
ลำดับการสร้าง subtask ให้เรียง DB → BE → FE → QA → DOC ตามลำดับการทำงานจริง

### Labels

ทุกใบต้องมี label เหล่านี้ เพื่อให้ filter ย้อนกลับหาต้นทางได้

- `brd-<nnn>` เช่น `brd-001` — ใช้ดึงงานทั้ง BRD
- `fr-<nnn>` เช่น `fr-002` — ใช้ดึงงานของ FR เดียว (Epic ไม่ต้องมี)
- `sa-generated` — บอกว่าการ์ดนี้ถูกสร้างจาก flow นี้ ไม่ได้พิมพ์มือ
- label ของชั้นงานตัวเล็ก เช่น `be`, `db`, `qa` (เฉพาะ Subtask)

### เทมเพลต Description

ส่งเป็น markdown ผ่าน `contentFormat: "markdown"` (Jira จะแปลงเป็น ADF ให้เอง)

**Story**

```
**อ้างอิง:** BRD-001 / FR-002 / UC-002 / US-002

### สิ่งที่ต้องได้
<สรุป 1-3 บรรทัดจาก User Story>

### Acceptance Criteria
- [ ] <คัดลอกจาก AC ใน SA ทุกข้อ ห้ามตัดทิ้ง>

### กฎธุรกิจที่เกี่ยวข้อง
- BL-001 <ข้อความกฎ>

### Test Case ที่ต้องผ่าน
TC-005, TC-006, TC-007, TC-008, TC-009

### Definition of Done
- [ ] Unit test ครอบคลุม TC ที่ระบุและผ่านทั้งหมด
- [ ] Code review ผ่าน
- [ ] อัปเดต Swagger แล้ว
- [ ] ทดสอบบน dev environment ผ่าน
```

**Subtask**

```
**อ้างอิง:** FR-002 / UC-002 (Step 3-6)

### ขอบเขตงาน
- <งานย่อยที่ต้องทำ ระบุไฟล์หรือ layer ที่คาดว่าจะแตะ>

### รายละเอียดทางเทคนิค
- Endpoint / Table / DTO / Validation ตาม API Contract ข้อ 5 ของ SA

### เสร็จเมื่อ
- [ ] <เกณฑ์ที่ตรวจได้>
```

### กฎการสร้างการ์ด

1. ถามหรือตรวจ project key ก่อนทุกครั้งด้วย `getVisibleJiraProjects` ห้ามเดา key
2. ตรวจ issue type ที่ project รองรับด้วย `getJiraProjectIssueTypesMetadata` ก่อน เพราะบาง project ใช้ `Sub-task` ไม่ใช่ `Subtask` และบาง project ไม่มี Epic
3. สร้างตามลำดับ Epic → Story → Subtask เพื่อให้ผูก `parent` ได้ถูก
4. ก่อนสร้าง ให้สรุปรายการการ์ดทั้งหมดให้ผู้ใช้ดูเป็นตารางก่อน ถ้าจำนวนเกิน 10 ใบต้องขอคำยืนยันก่อนลงมือ
5. ตรวจซ้ำด้วย `searchJiraIssuesUsingJql` ว่ามี label `fr-<nnn>` อยู่แล้วหรือไม่ ถ้ามีให้อัปเดตใบเดิมด้วย `editJiraIssue` ห้ามสร้างใบซ้ำ
6. ห้ามกำหนด assignee เองถ้าผู้ใช้ไม่ได้ระบุ
7. Jira แบบ Scrum board จะเห็นการ์ดเฉพาะที่อยู่ใน active sprint ต้องแจ้งผู้ใช้ว่าการ์ดที่สร้างใหม่จะอยู่ใน Backlog และต้องลากเข้า sprint เอง เพราะ MCP ยังไม่มี action จัดการ sprint

### สิ่งที่ต้องรายงานกลับเมื่อเสร็จ

ตารางเดียวที่มีคอลัมน์ `FR | Jira Key | ระดับ | Summary | Parent` แล้วปิดท้ายด้วย

- FR ที่ยังไม่มีการ์ด (ถ้ามี) และเหตุผล
- NFR ที่ยังไม่ถูกแปลงเป็นการ์ด
- สมมติฐานที่ตั้งไว้ระหว่างวิเคราะห์ และจุดที่อยากให้ผู้ใช้ยืนยัน
